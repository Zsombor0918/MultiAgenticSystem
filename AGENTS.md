# Contributor instructions

Read `README.md`, `WORK_PLAN.md`, and `docs/RESEARCH_ALIGNMENT.md` before working here. They define the user's intended system, the research behind it, and the build order. Follow the current user's clarified requirements over older research recommendations; do not silently simplify away core capabilities. Update progress only with evidence.

The normal workflow starts with ideas discussed in ChatGPT and an approved strategic GitHub issue created through the GitHub plugin. Crew then produces a technical plan for review/approval, a detailed implementation plan with proposed code changes for approval, and coordinated implementation, checks, independent review, and delivery. Smart selection of backend/agent/model/effort/skills/tools, tool capability knowledge, credit/usage-aware decisions, and smart context handling are core requirements in planning and execution. Monitoring is not merely a later optional report.

Minimize total implementation and maintenance effort. Prefer Crew's existing capabilities and reviewed components, but treat research findings as a starting point: try better alternatives or compare a few candidates when needed. A focused custom implementation is acceptable when it is simpler or more reliable than adaptation. Explain meaningful changes, tradeoffs, and evidence to the user; discuss changes to core scope, architecture, or schedule before committing to those changes. Do not replace the user's intended agent/skill system with a generic fixed pipeline. Keep the product reusable across projects and preserve each target's instructions, permissions, Git conventions, and CI. TARS is the architectural inspiration; do not assume an available TARS package.

Aim for a usable first integrated version in about one week, following the tentative schedule in `WORK_PLAN.md`. Timebox component experiments, commit useful progress, and flag schedule risks early. This is a target, not a claim that unverified capabilities will work or a reason to drop core requirements.

Keep **Kiro Crew: Start** in `.vscode/tasks.json` as the single normal startup entry point. Integrate shared library/configuration and any required supporting startup with its launcher; normal operation must not require additional startup tasks or commands. Preserve necessary first-time setup, login, and approvals, and verify startup-related changes.

Develop directly in this repository with ordinary Git commits for completed, checked steps. Do not create a Git worktree for work here. Distinguish proposals, documented capability, and observed behavior. Preserve historical research and attribution. Do not commit credentials, runtime data, raw agent transcripts, or generated test artifacts.

Original project work is licensed under `AGPL-3.0-only`; preserve `LICENSE` and the README's licensing notice. Check license compatibility and retain upstream notices when adopting third-party components. Do not imply that this repository's license relicenses separate dependencies or target projects.

Kiro Crew is selected and trusted; do not reopen the runtime choice or re-benchmark its foundation. Read `docs/research/CREW_EXTENSIONS_2026-11-16.md` for the current extension plan. Reuse native features first, then ready-made Crew extensions, then portable/adapted components, and write only the remaining gaps. The broader complete-system comparison is supporting research. Preserve required upstream assets and distinguish persona skills from registered Crew agents. Acceptance checks should target the extension integration.

For the next bounded implementation run, follow `docs/NEXT_STEP.md`: the existing AI-DLC Studio Crew extension, with real planning/review and user-gate evidence. Its stop-on-first-mandatory-failure rule overrides the general flexibility to try alternatives within that run: preserve evidence, report the failure, and revise the approach with the user before retrying.
