### II.3. Kérés, run ID és befejezés

1. A koordinátor az eredeti `engine log review` paranccsal nyitja meg a `REVIEW_REQUESTED` kérést. Megmarad a stage, attempt, reviewer, `requestId`, `reviewFile`, `reviewed_at` és a visszaadott `recordVerdict` parancs. Az egyszeri indítási foglalás ugyanezt a nyitott kérést és a kötött koordinátor sessiont használja az AI-DLC meglévő audit zárolása alatt. Az eligibility és a foglalás egy zárolt művelet, amely a tool futása előtt véget ér. A `task` szövegében szereplő azonosító vagy fájlnév egyeztetési adat. A hiteles érték a review-kérésből érkezik.
2. A PreToolUse az eredeti ellenőrzések után lefoglalja a kérést. A PostToolUse a Crew hiteles eszközazonosítójával érkező `tool_response.output` tényleges `Spawned` vagy `Queued` nyugtájából rögzíti a run ID-t. A Crew ezen az úton 2000 karakterre korlátozza a kimenetet. Az eredeti `tool_input` nincs a PostToolUse payloadban. A pilot a szülő session egyetlen nyitott foglalásához köti az egyetlen elfogadott run ID-t. A Crew ág a `SUBAGENT_DISPATCHED` sort egyszer írja, az admission nyugta alapján. A `SubagentStop`-ból átvett audit feldolgozást a valódi terminális esemény indítja. Az ismeretlen, sérült vagy elveszett nyugta egyeztetésig nyitva marad. [Hiteles PostToolUse payload](https://github.com/kirodotdev/KiroCrew/blob/v0.13.0/src/kiro_crew/dashboard/chat_turn/tool_results.py#L930) · [Crew nyugta](https://github.com/kirodotdev/KiroCrew/blob/v0.13.0/src/kiro_crew/mcp_tools/spawn.py#L573)
3. A Studio a repohoz és intenthez kötött szülőslotból, a foglalás idejétől olvassa a `HostBridge.recent_rows(..., roles=("subagent",))` sorokat. A default `("user", "queued")` szűrés kihagyja ezeket a sorokat. Csak a megfelelő `meta.subagentCompletion` `kind="single"`, `outcome="ok"`, `agentId=run ID`, `agentName=reviewer` értéke igazolhat sikeres worker befejezést. Az audit az eredeti requesthez írja a `SUBAGENT_COMPLETED` bizonyítékot, az eredeti `reviewFile` olvasott, változatlan lenyomatával. A worker és a koordinátor nem írhatja át ezt a hiteles nyugtát. [Crew sor szerepe](https://github.com/kirodotdev/KiroCrew/blob/v0.13.0/src/kiro_crew/dashboard/chat_turn/queue_drain.py#L1141) · [Crew completion mezők](https://github.com/kirodotdev/KiroCrew/blob/v0.13.0/src/kiro_crew/subagent_completion_meta.py#L37)
4. A `review --verdict` az eredeti fájlból olvas, ellenőrzi a konkrét run és request egyezését, majd a meglévő szabályok szerint rögzíti a `READY` vagy `NOT-READY` eredményt. A review-fájl megjelenése és a start nyugta a kérés nyitva maradása mellett is lehetséges. A meglévő `orchestrate wait --for review` a fájlt figyeli, a terminális egyezést az audit bizonyítja. A pilot az elfogadott, még futó workerre a meglévő `aidlc-continue-workflow.ts::isPendingSubagentStop()` várakozási útját használhatja. Ha szükséges, a fogadott és lezárt runhoz kösd a már létező in-flight jelzést. A normál AI-DLC javítási kör és emberi kapu a rögzített verdiktre reagál.
5. Egyeztetéskor, leálláskor vagy újranyitáskor használd a meglévő kérés és run kötést. A `HostBridge` memóriájából hiányzó sor még nem végállapot. A scope szerint elérhető Crew futási rekord segíthet az egyeztetésben. Ha a terminális eredmény vagy az egyezés nem bizonyítható, hagyd nyitva a review-t. A teljes `spawn_status` eredmény olvasása elszámolhatja a completiont, ezért az eseményre épülő pilot ne erre várjon. Duplikált completion ugyanazt a feldolgozott audit sort adja vissza.
